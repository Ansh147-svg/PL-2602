@app.route("/", methods=["GET", "POST"])
def home():
    conn = mysql.connector.connect(**db_config)
    cursor = conn.cursor()

    # Updated table schema with gender and role columns
    cursor.execute("""
        CREATE TABLE IF NOT EXISTS users (
            name VARCHAR(100),
            gender VARCHAR(50),
            role VARCHAR(100)
        )
    """)

    if request.method == "POST":
        username = request.form.get("username")
        gender = request.form.get("gender")
        role = request.form.get("role")

        if username and gender and role:
            cursor.execute(
                "INSERT INTO users (name, gender, role) VALUES (%s, %s, %s)",
                (username, gender, role)
            )
            conn.commit()

    cursor.execute("SELECT name, gender, role FROM users")
    rows = cursor.fetchall()

    cursor.close()
    conn.close()
    return render_template_string(html, rows=rows)

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000, debug=True)

Docker Image Scanning - Trivy
==============================
Clone "https://github.com/KastroVKiran/ECR-ECS-Project.git"

docker build -t myapp:v1 .

sudo yum install -y yum-utils
sudo yum-config-manager --add-repo https://aquasecurity.github.io/trivy-repo/rpm/releases/x86_64/
sudo rpm --import https://aquasecurity.github.io/trivy-repo/rpm/public.key
sudo yum clean all
sudo yum install trivy -y

trivy --version

Scan Your Docker Image
Your image: myapp:v1

Run:
trivy image myapp:v1

The above command might show error, the error is not because of trivy or scanning, it is because of insufficient disk space in the VM. 
While running Trivy, it tried to download the Java vulnerability database (~800 MB) into /tmp, but your EC2 instance ran out of storage. This is very common on t2.micro / small EC2 instances.

To check disk size
df -h

On the first run, Trivy insists on downloading the Java vulnerability database into /tmp path. And Because your /tmp is only 481 MB, the Java DB download (~834 MB) fails.
The simplest and correct solution is to change the temporary directory used by Trivy so that the download happens on your main disk (/), which has ~26 GB free.

Create a New Temporary Directory
mkdir -p /home/ec2-user/trivy-temp

Tell Linux to Use That Directory Instead of /tmp
Set the TMPDIR environment variable:
export TMPDIR=/home/ec2-user/trivy-temp

Verify it:
echo $TMPDIR

Expected:
/home/ec2-user/trivy-temp

Run the Scan Again
trivy image myapp:v1

Now the Java DB (~834 MB) will download into:
/home/ec2-user/trivy-temp
instead of /tmp.

Once the Java DB is downloaded once, future scans can skip it:
trivy image --scanners vuln --skip-java-db-update myapp:v1
This makes scanning much faster.

Generate Reports - JSON report (for CI/CD)
trivy image -f json -o trivy-report.json myapp:v1

ls ----> You will see the json file ---> cat <JSON_FILE_NAME>

View the JSON Report ---->
If jq is installed, use:
jq . trivy-report.json

Install jq if needed:
sudo yum install jq -y

Then filter vulnerabilities:
jq '.Results[].Vulnerabilities[] | {PackageName, VulnerabilityID, Severity, InstalledVersion, FixedVersion}' trivy-report.json
jq '.Results[].Vulnerabilities[] | {PkgName, VulnerabilityID, Severity, InstalledVersion, FixedVersion}' trivy-report.json

See only the highly risk vulnerabilities;
trivy image --severity HIGH,CRITICAL --exit-code 1 myapp:v1

Understand the Vulnerability Fields
Typical report section:
Field			Meaning
PackageName	vulnerable package (This tells which package is vulnerable.)
VulnerabilityID	CVE identifier (CVE = Common Vulnerabilities and Exposures)
Severity			risk level
InstalledVersion	version inside image
FixedVersion	version that fixes issue

Where These Vulnerabilities Come From?
Your Dockerfile:
FROM nginx:latest
COPY . /usr/share/nginx/html/
EXPOSE 80

Vulnerabilities usually come from:
Source			Example
Base OS			Debian packages
Libraries		openssl
System tools		curl
Web server		nginx

So the vulnerabilities are not from your application code. They come from the base image.

How DevOps Engineers Fix Vulnerabilities
Method 1 — Change Base Image
Instead of:
FROM nginx:latest

Use:
FROM nginx:alpine

Why?
Image		Size			Vulnerabilities
nginx:latest	~164 MB	more
nginx:alpine	~23 MB		fewer

Method 2 — Update Packages
Example:
RUN apt-get update && apt-get upgrade -y
This installs patched packages.

Method 3 — Use Minimal Images
Better base images:

Image	Type
alpine	minimal
distroless	production secure
scratch	ultra minimal

Method 4 — Remove Unnecessary Packages
Example:
remove compilers
remove debugging tools
remove unused libraries
