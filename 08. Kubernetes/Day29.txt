Step 1 — StorageClass for EBS CSI
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-sc	# Name of the StorageClass (used in PVCs via storageClassName)
provisioner: ebs.csi.aws.com  # CSI driver for EBS  # Ensures volumes are dynamically created in AWS when PVC requests storage
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Delete
parameters:
  type: gp3	#AWS EBS volume type (gp3 = General Purpose SSD, newer than gp2)

volumeBindingMode: WaitForFirstConsumer ensures the volume is created in the same AZ as the pod.
reclaimPolicy: Delete means the EBS volume is deleted automatically when the PVC is deleted.

🔹 Summary of What This StorageClass Does
Defines a dynamic storage provisioning template for AWS EBS.
When a PVC requests storage with storageClassName: ebs-sc:
	Kubernetes uses the AWS EBS CSI driver.
	Creates a gp3 EBS volume.
	Binds it to the Pod’s node AZ (thanks to WaitForFirstConsumer).
	Deletes the EBS volume when the PVC is deleted (Delete policy).

Apply it:
kubectl apply -f storageclass.yaml

#Check for storage class
kubectl get sc ----> You will see "ebs-sc" storage class got created

Step 2 — PVC YAML
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: ebs-pvc	# Name of the PVC (referenced by Pods to mount storage)
spec:
  accessModes:	#Volume can be mounted as read-write by a single node
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi	# Requesting 5GiB of storage
  storageClassName: ebs-sc		 # Refers to the StorageClass (ebs-sc) we created earlier

🔹 What Happens When You Apply This PVC
Kubernetes sees storageClassName: ebs-sc.
The ebs-sc StorageClass provisions a gp3 EBS volume of 5Gi.
A matching PersistentVolume (PV) is created dynamically.
This PVC (ebs-pvc) binds to that PV automatically.
A Pod can then mount this PVC and use it for persistent storage.

kubectl apply -f pvc.yaml
kubectl get pvc
#Currently the PVC will be in PENDING State. Because there is no pod which is claiming. Once we create the pod, then we will see the status as BOUND

Step 3 — Deployment YAML (nginx)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-ebs-demo
spec:
  replicas: 1
  selector:		# Defines how to identify the pods managed by this Deployment
    matchLabels:
      app: nginx-ebs		# Match pods with label "app=nginx-ebs"
  template:			 # Pod template (used to create new Pods)
    metadata:
      labels:
        app: nginx-ebs	# Label assigned to Pods (must match selector above)
    spec:
      containers:
      - name: nginx
        image: nginx
        volumeMounts:	# Mounts a volume inside the container
        - name: ebs-storage	# Refers to the volume defined below
          mountPath: /usr/share/nginx/html # Mount path inside the container # Anything stored here will persist in the EBS volume
      volumes:
      - name: ebs-storage		# Defines the volume to mount
        persistentVolumeClaim:
          claimName: ebs-pvc	# Uses the PVC we created earlier (ebs-pvc) # PVC dynamically provisions a gp3 EBS volume via 																		StorageClass

kubectl apply -f deployment.yaml
kubectl get pods

Note: If you access the app using URL, you will see error, because;
nginx doesn’t have permission to read files in the mounted volume, or the directory is empty and nginx doesn’t allow directory listing by default.

Since you mounted the EBS volume to /usr/share/nginx/html, here’s what’s happening:

Why 403 appears
	Empty volume mount:
		EBS volume is empty when first created.
		nginx expects index.html or directory listing.
		If none exists, nginx returns 403.
	Permission issues:
		The directory inside the pod may be owned by root, but nginx runs as www-data (or nginx user).
		nginx cannot read/write → 403.

So we will write the data in "/usr/share/nginx/html" location
Anything written to /usr/share/nginx/html inside the pod is persisted to EBS.

Note: Here we have 1 replica, if we have multiple replicas, then the VOLUME gets attached to which pod?
	EBS volumes only support ReadWriteOnce (RWO):
		AccessMode					Meaning
		RWO						Only one node can attach the volume at a time.
		ReadWriteMany (RWX)		Multiple nodes/pods can mount simultaneously.
		ReadOnlyMany (ROX)			Multiple nodes/pods can mount as read-only.

Lets scale the deployment and see what happens;
kubectl scale deployment nginx-ebs-demo --replicas=3

kubectl get pods ---> You will see 3 pods
Lets check the volumes attached to 3 pods;
kubectl get pod -o custom-columns=NAME:.metadata.name,STATUS:.status.phase,VOLUME:.spec.volumes[*].persistentVolumeClaim.claimName

You will see all the pods attached to same volume. But how? As I said, EBS support RWO only. So how this happened?
Kubectl get pods -o wide
You will see all the pods are running on same node.
How and why?

EBS volumes are ReadWriteOnce (RWO):
	Only one pod on one node can mount the volume at a time.
	The fact that all 3 pods show “Running” is possible because your pods ended up scheduled on the same node, but in reality only one pod can write at a time.
	If pods are on different nodes, the additional pods would remain Pending.

Kubernetes scheduler enforces this: it will only place pods that use that PVC on the node where the volume can attach.
You have 2 nodes, but the volume was attached to node 1 first.
Kubernetes sees that RWO volume is only attachable on node 1, so it schedules all pods which are using same PVC on node 1 only.
Node 2 cannot host these pods because the volume cannot attach there.

✅ Key insight
RWO EBS volume is “node-bound” → all pods using the same PVC end up on the same node.
This is scheduler behavior to satisfy volume attachment rules, not a bug.

✅ STEP 4 – Create Custom StorageClass (Retain Policy)

storageclass-retain.yml

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: retain-gp3
provisioner: ebs.csi.aws.com
# Retain ensures volume is NOT deleted when PVC is removed
reclaimPolicy: Retain
volumeBindingMode: WaitForFirstConsumer
parameters:
  type: gp3

Apply:

✅ STEP 6 – MySQL StatefulSet (5Gi Persistent Volume)

mysql-statefulset.yml

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql   # Must match headless service
  replicas: 1
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: mysql:8
          env:
            - name: MYSQL_ROOT_PASSWORD
              value: rootpass
            - name: MYSQL_DATABASE
              value: appdb
          ports:
            - containerPort: 3306
          volumeMounts:
            - name: mysql-data
              mountPath: /var/lib/mysql
  volumeClaimTemplates:
    - metadata:
        name: mysql-data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: retain-gp3
        resources:
          requests:
            storage: 5Gi

Apply:
kubectl apply -f mysql-statefulset.yml

Check:
kubectl get pods
kubectl get pvc

        conn = get_connection()
        cursor = conn.cursor()

        cursor.execute("""
            CREATE TABLE IF NOT EXISTS users (
                id INT AUTO_INCREMENT PRIMARY KEY,
                name VARCHAR(100),
                email VARCHAR(100),
                gender VARCHAR(20)
            )
        """)

        cursor.execute(
            "INSERT INTO users (name, email, gender) VALUES (%s, %s, %s)",
            (name, email, gender)
        )

        conn.commit()
        cursor.close()
