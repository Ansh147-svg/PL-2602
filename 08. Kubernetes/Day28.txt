2. Node Affinity
A more advanced and flexible version of Node Selector
Two conditions;
	preferred		- soft rule
	required		- hard rule

requiredDuringSchedulingIgnoredDuringExecution	---- hard rule --- must and should be followed
preferredDuringSchedulingIgnoredDuringExecution	---- soft rule

Operators;
In - the node must have the label key, and its value must match with one of the given values
- key: env
   operator: In
   values: 
	- dev
	- test

NotIn - the node must have the label key, but its value must NOT match with the given values
- key: env
   operator: NotIn
   values: 
	- dev
	- test

Exist - the node must have the label key, regardless of the value
- key: env
   operator: Exist

DoesNotExist - the node must not have the label key
- key: env
   operator: DoesNotExist

apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec: 
  replicas: 1
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
        - name: frontend
          image: nginx

apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-podantiaffinity
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
        - name: backend
          image: nginx

      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values:
                        - frontend
                topologyKey: kubernetes.io/hostname

vi app1-deploy.yaml ---->
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app1-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: app1
  template:
    metadata:
      labels:
        app: app1
    spec:
      containers:
        - name: app1
          # Change image name here when using other images
          image: kastrov/app1-image:latest
          imagePullPolicy: Always
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: app1-service
spec:
  selector:
    app: app1
  ports:
    - port: 80
      targetPort: 80

vi ingress.yaml ----->
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: apps-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - http:
      paths:
      # DEFAULT route → app1
      - path: /
        pathType: Prefix
        backend:
          service:
            name: app1-service
            port:
              number: 80

      # Route to app2
      - path: /app2
        pathType: Prefix
        backend:
          service:
            name: app2-service
            port:
              number: 80

      # Route to app3
      - path: /app3
        pathType: Prefix
        backend:
          service:
            name: app3-service
            port:
              number: 80

=> Resource Quota and Limit Ranges
A RQ in K8s limits the total amount of compute resources such as CPU, Memory, Object Count within a namespace

requests	--- the minimum amount of a resource that the container/pod is guaranteed to get
limits --- the maximum amount of a resource that the container is allowed to use

request: 0.5 Gi
limit: 1 Gi

requests should always be less than or equal to limits

CPU - cores
Memory - bytes

1 CPU = 1000 millicores / milliCPUs
0.5 CPU = 500 millicores / milliCPUs
0.2 CPU = 200 millicores / milliCPUs


resources:
	requests:
		cpu: 200m
	limits:
		cpu: 500m

resources:
	requests:
		memory: 256Mi
	limits:
		memory: 512Mi


spec:
	hard:
		pods: 10
		services: 5
		volumes: 5
